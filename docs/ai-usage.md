# Использование AI и проверка результата

Журнал фактической работы, а не список будущих возможностей. Обновляется по мере выполнения.

## Инструменты и разделение работы

Codex использован для разбора PDF, архитектуры, исходников React/TypeScript, SQL, тестов и настройки размещения. По просьбе пользователя подключены два агента: один проверяет требования/приёмку, второй - архитектуру и SQL. Основной агент интегрирует результат и запускает проверки. Навык PDF применялся для чтения задания, Sites - для рекомендаций по реализации и проверке интерфейса; пользователь выбрал GitHub и собственный VPS для публикации.

## Что потребовало исправления

- Первоначальная SQL-нормализация обрезала обычные пробелы, но допускала табуляции и переводы строк как содержимое. Проверка обнаружила расхождение с UI trim; триггер и SQL-тесты исправлены.
- Первоначальная адаптивная таблица скрывала категорию и дату. При проверке требований это выявлено; на узком экране эти поля перенесены во вторую строку карточки.
- Для повторного создания при сетевой неопределённости оставлен UUID одной попытки. Конфликт ID не считается успехом без чтения своей записи и сравнения содержимого; upsert не используется.
- pnpm сначала запретил postinstall esbuild. Явно разрешена сборка только этого пакета через pnpm-workspace.yaml.
- Локальные UI-запуски столкнулись с изоляцией preview и тестового браузера. Тест умеет запускать собственный preview в одном окружении. Использован установленный Chromium, без доступа к личному браузеру пользователя.
- Первый frontend bundle превышал 500 KB. Supabase выделен в отдельный chunk, после чего сборка проходит без этого предупреждения.
- На ретрансляторе уже были заняты 80/443. Вместо второго proxy добавлены точные SNI-маршруты; n8n вынесен на более ёмкий VPS и доступен через SSH-туннель. Reload Caddy прервал текущие proxy-соединения; после переподключения существующие службы и маршрут проверены.

## Выполненные проверки

- TypeScript и production build.
- Восемь unit-тестов логики, включая классификацию ограничений Auth.
- Реальная локальная PostgreSQL-проверка миграции и всех SQL-тестов A/B/anon в PGlite; варианты с автоматическим RLS и без него прошли.
- Изолированный UI-сценарий с mock API: маршруты входа/регистрации, список, дата/категория на 360px, отсутствие горизонтального скролла, фильтр/поиск, обязательные поля, двойная отправка и редактирование.
- Визуально просмотрены снимки desktop/mobile и страницы входа.
- Опубликованная сборка проверена из изолированного браузера с реальным Supabase Auth initialization: экраны входа/регистрации загружаются, ошибок JavaScript и горизонтального скролла на 390px нет. Аккаунты этим тестом не создавались.
- Живой Supabase до миграции отвечал отсутствием таблицы; после сообщения владельца о применении SQL неавторизованный SELECT возвращает 42501 permission denied, как ожидается.

## Что пока не доказано

Полный сценарий с реальными A/B в Supabase, независимая проверка почтового сценария и обработка потерянного ответа в живой сети ещё не подтверждены. Локальные SQL/UI-тесты не выдаются за эти проверки. Живой Telegram `/start` с двумя кнопками и callback подтверждён пользователем 31 октября; полная демонстрационная матрица остаётся открытой. Исследование Instagram завершено в отдельной ветке `docs/instagram-plan`; интеграция веток ещё не завершена.

Пользователь выбрал custom SMTP с подтверждением email. Подтверждение не отключалось. Настройка отправителя выполняется в Dashboard, credentials не включаются в исходники.

Пользователь сообщил об успешной регистрации/входе и работе приложения после настройки SMTP. При этом письмо пришло, а UI показал ограничение частоты. Без Auth logs нельзя утверждать точную причину ответа 429. Исправлено поведение интерфейса: отдельный экран ожидания почты, нейтральное объяснение при rate limit, отдельный resend и пауза 60 секунд. Успешный signup, двойная отправка и ответ 429 проверены UI-тестом с mock API без отправки реальных писем.

## Повторная проверка и исправления 31 октября

Пользователь сообщил о неудобстве мобильной версии, незаметном результате сохранения и молчащем боте. Повторная сверка PDF показала, что удобство телефона и видимый результат сохранения — обязательные критерии, а локальные проверки сами по себе не доказывают живую работу бота.

- Основной агент исправил мобильную раскладку: сохранены категория и дата, поля ввода имеют размер 16px, основные элементы управления — touch target 44px и больше. Проверены ширины 320/375/390/414/768px.
- Вместо уведомления только в потоке списка добавлен фиксированный toast на 10 секунд после создания и изменения. UI-тест теперь проверяет его появление после обеих операций и расположение внутри viewport, а также отсутствие дубликата при double submit.
- После изменений основной агент выполнил 8 unit-тестов и UI-тест с подменённым API; проверки прошли. Реальный мобильный сценарий опубликованной сборки и независимый живой A/B-тест остаются открытыми.
- Telegram `getMe` подтвердил `BotTaskGame` / `ZmeiiniyBot`. Свежий webhook timeout и pending update показывают, что проверка доставки ещё не завершена. Основной агент переносит webhook с RU-ретранслятора на прямой DE HTTPS endpoint:88; успех переноса и живой ответ здесь не заявляются.
- В Instagram-ветке завершено исследование официальных Meta API, включая текущий Unified Login, два альтернативных пути, метрики и ограничения; подготовлены схема, план проверки и вопросы компании. Реальные аккаунты Meta не подключались, как и предусмотрено заданием.

Актуальные пробелы и границы доказательств собраны в [статусе приёмки](acceptance-status.md). Демонстрации, живая A/B-проверка и интеграция веток остаются незавершёнными.

Опубликованная мобильная сборка повторно прошла изолированный UI-прогон с подменённым API. Telegram восстановлен через прямой DE HTTPS :88; native fixed collection заменён на private JSON node со штатным credential, без токена в env/workflow. 39 проверок включают фактические bindings экспорта; пользователь подтвердил две кнопки и нажатие. Подробный актуальный статус — docs/acceptance-status.md.
