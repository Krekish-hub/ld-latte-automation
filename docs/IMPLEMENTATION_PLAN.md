# План реализации и сдачи

Дедлайн: 31 октября 2026, 17:00 Asia/Chita. Время ниже - контрольные точки, а не обещание непрерывной работы агента между сообщениями. При задержке доступов двигаем независимые части, сохраняем резерв на публикацию и проверку.

## 1. Репозиторий и организация

Локальный репозиторий создан, базовые документы закоммичены; удалённый ещё не создан. Перед первой работой в компонентной ветке подтягиваем общую базу из main. Не используем force push и не переписываем историю. Каждая задача объединяется в main только после своих проверок; дефект исправляется в ветке компонента. develop не нужен.

| Ветка | Объём | Итог |
|---|---|---|
| main | общая документация и интеграция | воспроизводимая проверенная сдача |
| feat/requests-app | web, requests migration, проверки | опубликованный сервис |
| feat/telegram-n8n | services, fixtures, workflow | работающий бот и экспорт |
| docs/instagram-plan | официальное исследование | схема, план, метрики и диагностика |

Миграции именуем уникальными timestamp-префиксами; каждому компоненту свои файлы. Общие README/deploy правим последовательно. Два помощника проверяют требования и архитектуру; при реализации одному можно поручить Instagram, второму независимую проверку, основной агент интегрирует. Отдельные агенты не должны одновременно менять одну рабочую папку/ветку.

## 3. Этапы работ

### A. Подготовка

1. Создать пустой публичный репозиторий; привязать remote, отправить main и ветки.
2. Проверить Git diff на секреты перед push; не публиковать исходный PDF и чужие материалы без необходимости.
3. Пользователь создаёт Supabase-аккаунт/проект и Telegram-бота; вводит секреты в локальные настройки или credentials.
4. Уточнить домен; проверить DNS и входящие 80/443. Подготовить локальный frontend .env.example и серверный .env.example.
5. Создать checklist приёмки и AI-журнал. Записывать фактические проверки, а не будущие намерения.

Готовность A: можно применить SQL, войти в приложение и зарегистрировать Telegram webhook; при отсутствии доступов продолжить B/C локально.

### B. Supabase и изоляция

1. Написать миграцию requests: ограничения, FK, default, timestamp-trigger, индексы, запрет изменения владельца и created_at.
2. Включить RLS, настроить grants и политики в одной миграции.
3. Применить к чистому проекту, сгенерировать TypeScript-типы.
4. Проверить anon, пользователя A и пользователя B прямыми API-запросами.
5. Проверить обязательные поля, чужой user_id при INSERT, подмену владельца при UPDATE и запрещённые значения.

Готовность B: сохранён отчёт о фактических отрицательных запросах; UI-фильтр не участвует в доказательстве изоляции.

### C. Веб-приложение

1. Каркас React/TypeScript/Vite, конфигурация окружения и понятная ошибка при её отсутствии.
2. Авторизация и сессия: регистрация, подтверждение email, вход, выход, callback.
3. Форма создания с валидацией и одним UUID на попытку; показать созданную заявку после успешного ответа.
4. Список: все обязательные колонки, поиск, статус, пагинация и пустые состояния.
5. Просмотр/редактирование: статус, конфликт обновления, ошибки доступа.
6. Адаптивность, клавиатура, фокус, блокировка submit, сохранение текста при ошибке.
7. Сборка, типы, lint и ключевые браузерные проверки.

Готовность C: сценарий от регистрации до повторного входа проходит в опубликованной сборке; данные в реальном Supabase, не в mock/localStorage.

### D. Telegram

1. services migration и отдельная роль чтения; проверить TLS-подключение из n8n.
2. Подготовить fixtures 0/2/5/9 и SQL для переименования/отключения/добавления.
3. Реализовать routing событий и динамический JSON-клавиатуры, отдельно пустой результат и ошибку.
4. Обработать callback по стабильному ID, подтвердить callback, повторно прочитать источник.
5. Проверить устаревшие кнопки и неизменность workflow при изменении таблицы.
6. Экспортировать workflow, удалить секреты/приватные значения; импортировать в чистую конфигурацию и связать credentials по инструкции.

Готовность D: живой бот и переносимый workflow, показаны все наборы и мутации данных.

### E. Instagram

1. Исследовать официальные Meta-документы; завести журнал источников и даты.
2. Выбрать основной путь входа, перечислить предусловия и роли владельцев; альтернативу описать отдельно.
3. Описать получение/продление/отзыв токенов и разрешения; не смешивать API-пути.
4. Составить таблицу метрик с endpoint, period, ограничениями, доступностью и ссылкой.
5. Спроектировать многопользовательский сбор, повторные загрузки, ошибки токенов и rate limits.
6. Подготовить схему, пошаговый план по ролям, проверки этапов и вопросы компании.

Готовность E: у каждого изменчивого технического утверждения есть официальный источник или явная отметка «нужно проверить». Недоступность документации не заменяем уверенными догадками.

### F. Размещение

1. Снять исходное состояние контейнеров, ресурсов и VPN. Проверить внешние порты и маршрутизацию.
2. Установить только необходимый Compose plugin совместимым способом; подготовить отдельный Compose project.
3. Задать volumes, лимиты памяти, ротацию логов, стабильный n8n encryption key.
4. Запустить Caddy, получить TLS, разместить готовую статическую сборку.
5. Настроить Supabase Site URL/redirects под реальное имя.
6. Запустить n8n, создать администратора, импортировать workflow, добавить credentials, включить production webhook.
7. Проверить editor isolation, HTTPS, запросы с внешнего устройства, ресурсы и работу VPN.
8. Сохранить резервную копию конфигурации и описание отката.

Готовность F: нет публичного 5678, редактор защищён, frontend и бот работают извне; существующие сервисы продолжают работать.

### G. Финальная приёмка

Пройти ACCEPTANCE.md на двух пользователях. Снять короткую демонстрацию всех обязательных сценариев. Проверить чистую сборку из репозитория и достаточность SQL/n8n-инструкций. Заполнить ограничения и AI-журнал фактическими результатами. Проверить ссылки в приватном окне/с другого устройства.

## 4. Что требуется от пользователя

| Действие | Почему нужно | Когда |
|---|---|---|
| Создать GitHub-репозиторий / включить доступный способ создания | текущий коннектор не создаёт репозитории, браузер отключён | до публикации исходников |
| Создать Supabase-аккаунт и проект | аккаунта ещё нет; условия принимает пользователь | до живой проверки БД/Auth |
| Создать бота через BotFather | получить отдельный тестовый токен | до живого webhook |
| Уточнить собственный домен или выбрать DNS-вариант | HTTPS и стабильные webhook URL | до размещения |
| Предоставить два тестовых email | проверить регистрацию и изоляцию | до финальной приёмки |

Код и документы не блокируются целиком ожиданием этих действий. Пароли и ключи вводятся в настройки, не в публичные файлы. Личные расходы/платные подписки отдельно не подразумеваются.

## 5. Если срок начинает сжиматься

Сначала сохраняем обязательные критерии: реальный Supabase, RLS, рабочий Auth и заявка, динамический бот, полный документ Instagram. Сокращаем декоративные эффекты, сложность навигации и необязательные расширения. Не заменяем проверку двух пользователей скриншотами UI и не сдаём workflow без живой проверки. Любой непроверенный компонент явно указываем в известных ограничениях.
