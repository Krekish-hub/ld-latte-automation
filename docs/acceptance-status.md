## Живой Supabase A/B: 23 проверки

[Машиночитаемый отчёт](verification/live-ab-20261031.json) фиксирует 23 успешные проверки через реальные Auth-сессии и PostgREST без mocks: password login A/B, разные principals, серверный owner/new, изоляция списка/чтения/изменения, защита owner forgery/reassignment и начального статуса, повторный ID, собственное редактирование, серверный updated_at и stale guard, редактирование B, поиск/фильтр, запрет anon и сохранность после повторного входа.

Временные пользователи созданы через явно разрешённый Auth Admin API с `email_confirm=true`. Настройки SMTP не менялись, обычная регистрация и доставка писем этим probe повторно не проверялись. Исходный HTTP-ответ probe был **500 / `ok=false`** из-за ошибки служебной проверки очистки: у service_role нет SELECT на requests. При этом `failure=null`, все 23 assertions выполнены. Grants не расширяли; независимый Supabase MCP SQL подтвердил **0 QA-users / 0 QA-requests**. Временная Edge Function заменена версией 2: JWT verification включена, ответ 410, привилегированный код удалён. Исходный результат сохранён в отчёте без подмены.

## Telegram: исправление и подтверждение

`getMe` подтвердил нужного бота: **first_name `BotTaskGame`, username `ZmeiiniyBot`**. Таймаут старого входа устранён: production webhook перенесён напрямую на DE-сервер, HTTPS порт **88**, с проверкой нативного secret header. Существующие Xray/VPN порты 443/8443 не менялись.

После восстановления доставки выявлено превращение динамического массива native fixed collection в пустые объекты. Отправка заменена на небольшой private node `CUSTOM.ldLatteTelegram`, использующий штатный зашифрованный `telegramApi` credential и обычное JSON-поле. Исходник, установка и экспорт находятся в репозитории. 39 тестов включают фактические bindings workflow для 0/2/5/9. Пользователь подтвердил: **«Две кнопки появились, нажатие работает»**. Авторизованный no-chat HTTP smoke возвращает 200 за 0.43 с, не отправляя сообщений. Эти первоначальные проверки подтверждали две кнопки и инфраструктуру; результат последующей полной автоматизированной матрицы приведён ниже.

Затем [автоматизированный production-прогон](verification/live-telegram-20261031.json) завершился **PASS: 9 стадий / 10 реальных Telegram API acknowledgements**. Проверены 5 и 9 кнопок, добавление десятой, переименование и выбор актуального имени по стабильному ID, отключение, устаревшая кнопка, пустой список и восстановление двух услуг. Дополнительное acknowledgement относится к выбору добавленной услуги. Для сопоставления использованы тип/текст ответа и количество кнопок; одного временного label недостаточно, поскольку пользователь мог нажимать кнопки дополнительно.

Входящие события — **синтетические fixtures с действующей webhook-аутентификацией**, далее работают настоящий production n8n workflow, Supabase и Telegram API. Это доказывает автоматизированную матрицу, но не Telegram-origin доставку каждого синтетического callback и не ручное прохождение всех этапов; реальный callback пользователя подтверждён отдельно. Граф/версия workflow не менялись. Временная output-only telemetry удалена, исходник Sender восстановлен побайтно. Независимый SQL подтвердил **9 services / 2 active / 0 QA**, health после перезапуска — **200**.
